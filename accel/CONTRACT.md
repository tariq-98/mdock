# mdock accelerator bridge: interface contract

Lets Linux containers in mdock use the Mac's media engine, GPU and Neural Engine. Each accelerator is
reached through an API Linux software already speaks, and the work runs natively on macOS.

```
container ──(unix socket via CDI mount, or TCP to <name>.mdock.internal)──▶ guest relay (socat)
          ──vsock──▶ mdock daemon (host) ──unix socket──▶ host service (native macOS process)
```

## Services

| Service | vsock port | Host socket (`$ACCEL` = `~/.mdock/accel`) | In-container endpoint | Owner |
|---|---|---|---|---|
| media-exec: remote ffmpeg/ffprobe | 1026 | `$ACCEL/media.sock` | unix `/run/mdock/accel/media.sock` (CDI `mdock.dev/media=ffmpeg`) | bridge core |
| vt: VA-API → VideoToolbox | 1027 | `$ACCEL/vt.sock` | unix `/run/mdock/accel/vt.sock` (CDI `mdock.dev/media=vaapi`) | `mdock-vt` |
| ml: Foundation Models + CoreML (HTTP) | 1028 | `$ACCEL/ml.sock` | `http://ml.mdock.internal:8100` | `mdock-ml` |
| llm: Metal llama.cpp (OpenAI HTTP) | 1029 | `$ACCEL/llm.sock` | `http://llm.mdock.internal:8200` | `mdock-llm` |
| llm-rpc: ggml RPC (Metal) | 1030 | `$ACCEL/llm-rpc.sock` | `llm.mdock.internal:50052` | `mdock-llm` |

Rules for every host service:

- It is an executable target in this package (`Sources/<name>/`), started as
  `<name> serve --socket <path>` [`--rpc-socket <path>` for mdock-llm]. It listens on a **unix stream
  socket** (mode 0600) and handles many concurrent connections. It must not open TCP ports reachable
  from the network; loopback-only helper processes are fine.
- The mdock daemon starts it **lazily** on the first guest connection, waits up to 10 s for the socket
  to appear, keeps it running, and stops it when mdock stops. Logs go to `$ACCEL/<name>.log`.
- Binaries are found next to the `mdock` binary (`.build/release/` in development, `Contents/MacOS/`
  in the app bundle).
- HTTP services speak plain HTTP/1.1 over the socket (the relay is byte-transparent), including
  streaming responses (SSE / chunked).
- Guest-side artifacts that must exist inside containers (e.g. the VA-API driver `.so`) are placed
  under `$ACCEL/guest/` on the host. The guest sees that directory at the identical path through
  virtiofs, and CDI specs bind-mount files from there into containers.

## CDI devices (generated by the guest at boot)

- `mdock.dev/gpu=all`: Vulkan via Venus (GPU engine only).
- `mdock.dev/media=ffmpeg`: mounts `/run/mdock/accel` and the ffmpeg/ffprobe shim at
  `/usr/lib/mdock/bin/` and over `/usr/lib/jellyfin-ffmpeg/`. Sets `MDOCK_SHARES` and
  `JELLYFIN_REMOTE_VIDEOTOOLBOX=1`.
- `mdock.dev/media=vaapi` (once `$ACCEL/guest/mdock_drv_video.so` exists): mounts `/run/mdock/accel` and
  the driver at `/usr/lib/mdock/dri/mdock_drv_video.so`. Sets `LIBVA_DRIVERS_PATH=/usr/lib/mdock/dri`,
  `LIBVA_DRIVER_NAME=mdock` and `MDOCK_SHARES`.
- ML/LLM need no device: any container can reach `*.mdock.internal`.

## Paths

The Mac's `/Users`, `/Volumes`, `/private` and `/private/var/folders` are mounted in the guest at
the same paths (virtiofs tags `users`, `volumes`, `private`, `folders`). A path inside a container
can be turned into a Mac path by reading `/proc/self/mountinfo`: for a virtiofs mount,
`host = share_root(source_tag) + mount_root + rest_of_path`. Files on container overlay storage or
named volumes live on the VM disk and are **not** visible to the Mac.

## Testing etiquette (shared machine)

- One mdock VM is shared by everyone: `DOCKER_CONTEXT=mdock`. Never stop or restart it and never
  switch engines; ask the bridge-core owner.
- Build only your own product with your own build directory:
  `swift build -c release --product <name> --build-path .build-<name>`.
- Don't edit files outside your own area. Put integration needs (guest packages, CDI mounts, env
  vars) in your final report.
