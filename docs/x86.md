# x86 images: Rosetta, FEX and hardware memory order

Containers are linux/arm64 by default. `--platform linux/amd64` or `linux/386` runs an x86 image
through a translator. Which one depends on the engine and on whether mdock's guest kernel is
installed (`mdock kernel status`; `mdock status` shows the result on its `x86:` line):

| | default engine | GPU engine |
|---|---|---|
| linux/amd64 | Rosetta | FEX (QEMU without mdock's kernel) |
| linux/386 | FEX (QEMU without mdock's kernel) | FEX (QEMU without mdock's kernel) |

Rosetta only runs under Virtualization.framework, so the GPU engine can't use it.

Two commands avoid translation altogether: `mdock arch-check IMAGE -- CMD` runs an image's arm64 and
amd64 variants side by side and reports differences, and `mdock port IMAGE` rebuilds an amd64-only
image as native arm64 by replaying its build.

## x86's memory order, in hardware

x86 guarantees that other cores see a core's stores in order (TSO); Arm doesn't. A translator either
puts barriers around memory accesses or, on Apple silicon, sets the core's TSO bit (ACTLR_EL1 bit 1)
so the hardware keeps x86's order, as Rosetta does on macOS. Inside a VM that needs the guest kernel
to switch the bit per thread, which stock kernels can't do. mdock builds its own:

- `kernel/build.sh`: Linux 6.18.56 from kernel.org (checksum and Greg Kroah-Hartman's signature
  checked) with Alpine's linux-virt configuration, Asahi Linux's TSO series (`PR_SET_MEM_MODEL`,
  as rebased by libkrunfw) and `0018-mdock-…`: a context switch only writes ACTLR_EL1 when the
  memory model changes. Each write traps to the hypervisor, and writing it on every switch made a
  native pipe round trip 24% slower.
- The VM's devices and ext4 are built in rather than modules, so the kernel boots without an
  initramfs ([architecture.md](architecture.md#boot)). A rebuild after a patch or config change only
  recompiles what changed: patched files keep their timestamps when their content is unchanged.
- `mdock kernel install` puts it in the guest (`mdock restart` boots it); `mdock kernel remove`
  goes back to Alpine's. The desktop app ships it.
- GPU engine: `gpu/patches/libkrun-hvf-tso.patch` lets the guest see and set the TSO bit through
  Hypervisor.framework (`HV_SYS_REG_ACTLR_EL1`, macOS 15+).
- Rosetta asks for TSO on its own, and keeps x86's order without it too. FEX (FEX-2610, built by
  `guest/build.sh` with `guest/patches/fex-mdock.patch`) runs without its FEXServer daemon, turns off
  Go's asynchronous preemption for the programs it runs (`GODEBUG=asyncpreemptoff=1`; Go's
  preemption signal crashed Go programs under FEX), and maps its 32-bit syscall page executable
  (32-bit musl crashed on it). FEX replaces QEMU wherever the kernel provides TSO; without mdock's
  kernel both engines fall back to QEMU for what FEX would run.

A message-passing litmus test (3000 × 4096 rounds) shows the effect:

| | reorderings |
|---|---:|
| arm64 program, Arm's memory order | 159–215 |
| arm64 program after `prctl(PR_SET_MEM_MODEL, TSO)` | 0 |
| x86-64 program on Rosetta (default engine) | 0 |
| x86-64 program on FEX (GPU engine) | 0 |
| x86-64 program on FEX told not to keep x86's order | 123 |

## Speed (M1)

| | Rosetta (default engine) | FEX (GPU engine) | QEMU | native arm64 |
|---|---:|---:|---:|---:|
| CPython loop | 0.56 s | 0.41 s | 3.97 s | 0.25 s |
| Python mix: dict / str / json / objects | 0.43 / 0.19 / 0.67 / 0.22 s | 0.35–0.47 / 0.17–0.19 / 0.58–0.66 / 0.19 s | | 0.27 / 0.11 / 0.43 / 0.12 s |
| `xz -3 -T1` / `-T4` / `pigz -p4` on a tar of /usr | 11.1 / 4.5 / 0.70 s | 9.6 / 4.0 / 0.72 s | | 6.0 / 2.8 / 0.62 s |
| Start a process (`/bin/true`, `perl -e 1`) | 11 / 33 ms | 19 / 58 ms | 13 / 38 ms | 0.3 / 1 ms |
| `docker build` running apt (curl, python3) | 40 s | 66 s | 69 s | 9 s |
| linux/386 sha256 / gzip / awk | FEX on both engines: 0.70 / 0.93 / 4.4 s | | 2.1 / 2.0 / 23.1 s | 0.77 / 0.70 / 1.5 s |

Native code doesn't pay for any of it: with patch 0018 a pipe round trip takes 24.7–24.9 µs
(Alpine's kernel: 25.2–25.5 µs). FEX compiles more code up front than QEMU, so short-lived processes
start slower; builds that run thousands of them (apt, dpkg) take about as long as on QEMU, and
everything that runs longer is 2–10× faster. For apt-heavy amd64 builds, the default engine is
quicker.

## Rosetta's ahead-of-time cache (`mdock set aot=on`)

Rosetta can keep translated code in a cache (rosettad in the VM, shared by every container through
`mdock-runc`), so a program isn't translated again on every run. It's off by default:

- Its translator dies on some binaries, e.g. the Node in `node:20-alpine` and `node:24-alpine`
  ("Not all x86 entry points were contained in a code segment"), and leaves an empty cache entry
  that then stops the program from starting. With `aot=on`, mdock drops such entries and restarts
  rosettad, so those programs fall back to plain Rosetta.
- It miscompiles others: `node:22-alpine` crashes on start. `--runtime runc` runs a container
  without the cache, and `-e ROSETTA_DISABLE_AOT=1` turns it off for one process.
- It's a trade-off even where it works. With it on, the Rosetta column above becomes: CPython loop
  1.11 s, Python mix 0.48 / 0.32 / 1.13 / 0.46 s, xz 8.3 / 3.7 / 0.64 s, process start 8 / 15 ms,
  apt build 38.5 s. Code translated ahead of time is faster for compiled C and starts sooner, but
  slower for an interpreter's dispatch loop.

## Keeping the kernel current

mdock's kernel doesn't follow Alpine's kernel updates (`mdock upgrade` updates Alpine's, which then
isn't booted). Rebuild it with a newer `VER` in `kernel/build.sh`, or `mdock kernel remove` to go
back to Alpine's. The kernel build keeps its object tree in the Docker volume `mdock-kernel-build`
(several GB) so rebuilds are quick; `docker volume rm mdock-kernel-build` reclaims the space.
